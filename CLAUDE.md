# FaveDay

## Product Goals

- **Vision**: A privacy-first desktop journal for daily mood and productivity tracking that turns simple 1-5 ratings into meaningful personal insights through analytics and pattern discovery.
- **Target users**: Individuals who want to reflect on their daily life, identify patterns in mood or productivity, and track personal wellness — with all data staying local and private.
- **Key pain points it solves**: Balancing quick daily logging (5-second entries) with meaningful analytics; maintaining privacy without cloud dependency; understanding personal patterns across months and years.
- **Current stage**: Production — fully featured desktop app with calendar, analytics, tag system, streak tracking, and search.

## App Overview

FaveDay is a personal daily scoring/journaling application built with Electron. Users rate their days with scores and add notes with tags.

## Architecture

- **Frontend**: HTML/CSS/JavaScript with Mustache templates
- **Backend**: Electron main process (Node.js)
- **Data Storage**: JSON files in user's data directory
- **Tag System**: Comprehensive caching system (`tag-cache.json`) for performance

### Key Files

- `app/js/faveday.js` — Main frontend logic, FaveDayApp class
- `app/main.js` — Electron main process, data handling
- `app/index.html` — UI templates (Mustache)
- `app/css/style.css` — Styling
- `app/lib/faveday/score-calculator.js` — Centralized score calculations (avg, median, quality)
- `app/lib/faveday/data-manager.js` — Centralized data access/persistence
- `app/lib/faveday/router.js` — Navigation, browser history, route parsing
- `app/lib/faveday/settings-manager.js` — User configuration UI
- `app/lib/faveday/config-store.js` — Synchronous config singleton (`window.configStore`); single source of truth, no `setConfig()` chains
- `tag-cache.json` — Cached tag statistics

### Tag System

- Regex `/([#@])\p{L}[\p{L}\d]*/gui` for tag detection. Two types: `#topic` and `@person`.
- Cache stores per-tag: `totalUses`, `avgScore`, `totalScore`, `hotness`, `firstUsage`/`lastUsage`, `yearStats`, `peakYear`/`peakYearCount`, `isPerson`, `recentActivity`.
- **Hotness algorithm**: `sum(score × max(0.01, 0.6^yearsAgo))` — extremely aggressive exponential decay. Current day weight 1.0, 1y ago 0.6, 3y ago 0.22, 5y ago 0.08, 10+y ago 0.006. Consistent long-term activity can compete with single recent mentions; sums each individual score weighted by recency (no averaging).
- Cache automatically updates on score save.

## UI/UX Patterns

- **Bento-grid dashboard widget order**: Year (calendar progress), Age (life progress), Coverage, Avg Score, Total Entries, Avg Words/Day, Last 5+ Score, Last 1 Score, Top Tag.
- **Tags page sorting** (7 options): Usage Count (default), Average Score, Total Score, Hotness, A-Z, Oldest (first usage), Newest (most recent usage). Sort controls live in the table header with active-state indicators.
- **Tag popup sparklines**: tiny per-year usage charts spanning the full diary timeline; bars (60% opacity, 2-12px height) for usage years scaled to the tag's max year, dim 2px dots (20% opacity) for empty years. Hover shows "Year: X uses" for every year.
- **Active vs passive button styling**: white underline marks active sort, gray text for passive — never reuse content-element colors (tags are blue, so meta-controls must NOT be blue).
- **No same colors for meta-controls and content elements** — meta UI must be visually distinct from data.

## Data Patterns

- CSS classes: `.tag` (topics), `.person` (people), `.recent` (recent activity).
- Popup data attributes: `data-tag`, `data-uses`, `data-avg`, etc.
- Sorting handles null values gracefully.
- Templates kept simple; logic stays in JavaScript.
- Global functions defined in `faveday.js` as `window.onFunctionName`.
- Mustache templates with partials.
- IPC bridge in `preload.js` for main/renderer communication.

## Development Best Practices

- **Single source of truth.** Score calculations all go through ScoreCalculator. Data access through DataManager. Settings through SettingsManager. No copies of config — read directly from `window.configStore`.
- **Avoid fallback duplication.** When the tag cache is missing fields, rebuild the cache (user can edit a score to trigger rebuild) — don't carry clunky fallback paths.
- **Leverage the tag cache** for sorting/aggregation rather than recalculating from raw entries.
